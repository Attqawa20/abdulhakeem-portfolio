The problem

Users of a service platform ask questions with different levels of risk. General questions about booking or supported services can be answered from an approved knowledge base. A question about a particular order, payment, or delivery requires current data from an authenticated system.

The Tranq AI assistant concept explores how to respect that distinction rather than generating plausible—but potentially false—answers.

Planning work to date

My earlier design discussions have explored an assistant knowledge base covering product workflows, customer, laundry-business, and rider roles, common intents, escalation rules, and privacy boundaries.

The central design rule is simple: the assistant should not invent live order statuses, prices, payments, or delivery events.

A grounded conversation flow

01 / STATIC INFORMATION

Explain the service

Use reviewed product help content to describe workflows and support policies.

02 / LIVE INFORMATION

Check source systems

Fetch order or payment data through authenticated APIs before answering account-specific questions.

03 / UNKNOWN

Say when data is missing

Give a transparent limitation or escalate instead of fabricating certainty.

04 / SAFETY

Protect customer data

Plan user verification, scoped tools, privacy safeguards, and human-support handoff.

Planned architecture, not a build claim

The intended AI Engineering capstone for 20 October 2026 to 20 January 2027 is a Tranq AI Operations Copilot. Its proposed learning and implementation areas include Python, LLM APIs, RAG, vector search, tool calling, MCP, agent orchestration, evaluation, and monitoring.

Status: This is a forward-looking technical plan. No working retrieval system, production agent, live API integration, or measured evaluation score is claimed.
